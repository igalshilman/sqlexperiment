# Delta-log experiment — 2026-10-10

Crate **0.11.0**, storage format **v11**, engine `turso_core` **0.8.2**.

This compares the original save path (publish every save through intent, objects
and head) with a durable delta log, in which a save commits by appending one
segment of changed page images (see the [protocol](../docs/PROTOCOL.md#delta-log)).
The log is folded into the page map through the original protocol after
`max_log_segments` appends. Both run the same code; the policy is a
`StorageOptions` field and never changes the format.

## Method

`benches/log_shipping.rs` replays one interleaved sequence per configuration:
a point read, a one-row update, a ten-row update in one transaction and a
one-row insert, 32 times (128 sessions, 96 saves). Every session reopens. With
the object cache, all sessions of a run share one `ObjectCache`, as one
long-lived owner process would. A final publish-every-save reader verifies all
writes.

Latency is the critical path in **round trips (RT)** from
`simulation::LatencyKv`. Each request costs one RT; concurrent requests overlap,
dependent ones add. Multiply by a backend RTT for wall time (the tables use
5 ms). Bandwidth, CPU and queueing are not modeled, so byte-heavy operations
look cheaper than they are. Counters come from `MemoryKv`. Results are
deterministic; the analyzer rejects repeats that differ.

```sh
cargo bench --locked --features simulation --bench log_shipping -- 2 > benches/results/log-shipping.csv
python3 benches/scripts/analyze_log.py
```

A *read session* is open plus query. A *write session* is open, query and save.
Bytes and mutation counts include the segment confirmation that open performs.

## Findings

- **Saves.** An append commits in 1 RT, against 5 RT (7 RT for larger saves) when
  every save publishes. With 4 segments, 80% of saves are appends and the mean
  save drops from 5–5.7 RT to 1.8–2.7 RT; with 16 segments, to 1.3–1.8 RT.
- **Folds are the tail.** A fold publishes every page logged since the last one
  and retires the segments, so its cost grows with the log. On 10,000 rows, folds
  take 7–11 RT with 4 segments and 16–17 RT with 16, against at most 7 RT for
  publishing every save. A larger log makes the mean better and the tail worse.
- **Opens pay for the log.** Open must re-put the last segment before exposing
  it (1 RT), because a failed append can leave a segment visible but not
  durable. Without a cache the probe also waits for the head (1 RT). With a
  cache, the probe joins the head read and an open costs 2 RT instead of 1. Read
  sessions get 0.8–1.0 RT slower with a cache, and 1.0–1.6 RT slower without one.
- **Net effect.** Write sessions get faster in every configuration: 9–31%
  faster without a cache and 22–45% faster with one. Read sessions get 19–26%
  slower without a cache and 47–94% slower with one, where reads are otherwise
  nearly free. The cache helps both designs more than the log does. On 10,000 rows it
  cuts write sessions from 21.5 to 10.2 RT when publishing every save.
- **Bytes and requests.** Each write session writes about 2× the bytes. Segments
  carry whole page images, each open rewrites the last segment to confirm it, and
  folds rewrite logged pages as objects. Probes issue `max_log_segments + 1`
  concurrent gets per open, mostly misses: up to about 25 gets per read with
  16 segments. Stored bytes grow by up to one full log of segments (a 3.9× peak on
  the 100-row database with 16 segments).

## Interpretation

The delta log is worth it for write-heavy, latency-bound owners with small
transactions, especially with an object cache, where it brings a write session
to the cost of two or three reads. Read-mostly workloads lose: every open pays
the confirmation. Folding often (about 4 segments) keeps the fold tail near the
publish-every-save cost while getting most of the save benefit.

## Possible improvements, not implemented

- **Overlap the confirmation** with the engine's first reads. This saves 1 RT
  only for cold sessions; with a warm cache there is nothing to hide it behind.
- **Skip confirmation for read-only sessions.** This weakens guarantees: a
  reader could observe a save whose outcome was uncertain and that a crash
  later removes.
- **Smaller probes** with an exact count hint in the cache, saving gets but not
  round trips.
- **Incremental folding** of the oldest segments, or folding concurrently with
  the next append, to cut the tail.
- **Byte-level deltas** instead of page images, to shrink segments and
  confirmations.

Remaining limits: simulated latency only, a uniform RTT for every request, no
bandwidth model, a single owner and no real backend.
