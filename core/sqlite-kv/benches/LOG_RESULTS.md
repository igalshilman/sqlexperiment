# WAL-native store results — 2026-10-11

Crate **0.11.0**, storage format **v12**, engine `turso_core` **0.8.2**.

This compares the WAL-native store (v12: a log of page images, pages checkpointed
in place, a small checkpoint record) with the previous format (v11: radix page
map, head, intent), both when it published every save and with its map-based
delta log. See [DESIGN.md](../docs/DESIGN.md) for the v12 design.

## Method

`benches/log_shipping.rs` replays one interleaved sequence per configuration:
a point read, a one-row update, a ten-row update in one transaction and a
one-row insert, 32 times (128 sessions, 96 saves). Every session reopens. With a
cache, all sessions of a run share one `PageCache` (v11: `ObjectCache`), as one
long-lived owner process would. Baselines are bulk loads that a later save has
checkpointed. A final reader verifies every write.

Latency is the critical path in **round trips (RT)** from
`simulation::LatencyKv`. Each request costs one RT; concurrent requests overlap,
dependent ones add. Multiply by a backend RTT for wall time (the tables use
5 ms). Bandwidth, CPU and queueing are not modeled. The _backend_ column says
whether a failed put can be visible without being durable (`weak`, the
simulator's default) or not (`strong`); weak backends make a fresh open confirm
what it did not write.

v11 rows come from `results/log-shipping-v11.csv`, produced by the v11 code (the
previous head of this branch) with a measurement fix backported: requests of a
concurrent phase are issued when queued rather than when first polled. The fix
did not change any v11 number. Results are deterministic; the analyzer rejects
repeats that differ.

```sh
cargo bench --locked --features simulation --bench log_shipping -- 2 > benches/results/log-shipping.csv
python3 benches/scripts/analyze_log.py
```

A _read session_ is open plus query; a _write session_ is open, query and save.
Mutations and bytes include open's confirmations.

## Findings

- **Saves are one round trip with a cache.** A commit is one put; checkpoint
  pages, garbage deletes and the claimed `meta` ride in the same round trip, with
  up to 64 mutations in flight. Every save with a cache takes exactly 1 RT. The
  worst v11 save took 11–17 RT. Without a cache a checkpointing save still needs
  a second round trip for `meta` (mean 1.05–1.64 RT).
- **With a cache, opens are one round trip.** Open reads `meta` and probes the
  log exactly to where this owner left it, in one round trip. Read sessions take
  1.00 RT (100 rows) and 1.66 RT (10,000 rows); write sessions 2.0 and 5.6 RT,
  against 6.0 and 10.2 RT for v11 publishing every save.
- **Cold opens fetch what queries need alongside replay.** Without a cache,
  open fetches every page of a database of at most 16 pages, or else the pages
  of the working-set hint (at most 32 by default).
  - 100 rows: a read session takes 2.0 RT on a strong backend and 3.0 RT on a
    weak one (plus confirmation), against 4.0 RT for v11, at 13.6 gets instead
    of 9.0.
  - 10,000 rows: a point-read session takes about 3.2 RT instead of 5.7, and a
    one-row insert 2.2 RT instead of 5.9. Open reads about 31 gets (about
    125 KB) instead of 8 (78 KB). A point query still pays a round trip when its
    leaf is not in the hint; scattered multi-row updates still pay per page.
  - Sequential scans read ahead and cost a few round trips.
- **Smaller logs are better.** `checkpoint_after = 4` needs fewer gets and less
  storage than 16, and with exact probing both open in one round trip.
- **The cost is bytes and storage.** Pages are written twice (log, then in
  place). A write session writes 1.0–1.8× the bytes of v11 publishing every save,
  and up to 2.8× on weak backends without a cache, which add the confirmation
  re-put. Retained log segments and garbage awaiting the next checkpoint raise
  stored bytes to 1.3× (10k rows, policy 4) to 4.9× (100 rows, policy 16) of v11.

## Interpretation

The log is what makes a single-put commit possible; once it exists, the map,
head and intent are redundant. A long-lived owner reaches one round trip per open
and per save. A cold owner fetches the previous owner's working set with replay, so its
first queries mostly avoid a round trip per B-tree level.

## Possible improvements, not implemented

- **Overlap confirmation** with the first query on weak backends: one round trip
  off cold opens, if nothing is returned or committed before it is acknowledged.
- **A `log_start` hint** from the host, so a cold open can probe the log together
  with `meta`: one round trip off cold opens.
- **`meta` off the critical path** for checkpointing saves without a cache.

Remaining limits: simulated latency only, a uniform RTT for every request, no
bandwidth model, a single owner and no real backend.
