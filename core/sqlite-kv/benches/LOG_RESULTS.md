# Commit record against log segments — 2026-10-18

Crate **0.11.0**, storage format **v14**, engine `turso_core` **0.8.2**.

This compares v14 (one commit record holding the log since the last
checkpoint, written by every commit; past 4 KiB its inline log is sealed into
a stored value, and large transactions' segments are stored beside it) with v13 (a log of segments under their own keys, and a checkpoint
record, `meta`). Both run on a strong backend: reads return durable values, so
v13 confirms nothing at open. See [DESIGN.md](../docs/DESIGN.md).

## Method

`benches/log_shipping.rs` replays one interleaved sequence per configuration:
a point read, a one-row update, a ten-row update in one transaction and a
one-row insert, 32 times (128 sessions, 96 saves). Every session reopens. With a
cache, all sessions of a run share one `PageCache`, as one long-lived owner
process would. Baselines are bulk loads that a later save has checkpointed. A
final reader verifies every write.

Latency is the critical path in **round trips (RT)** from
`simulation::LatencyKv`. Each request costs one RT; concurrent requests overlap,
dependent ones add. Multiply by a backend RTT for wall time (the tables use
5 ms). Bandwidth, CPU and queueing are not modeled. Results are deterministic;
the analyzer rejects repeats that differ.

v13 rows come from `results/log-shipping-v13.csv`, produced by the v13 code
(the previous head of main) with the bindings' cadence added to its policies.
Each version's _bindings_ policy is the one its Node.js and Python bindings
use: v13 60 transactions or 256 KiB, v14 32 transactions or 64 KiB, sealed
past 4 KiB. v14 at 16 transactions or 16 KiB, all inline, is the previous
v14 default. Checkpointed pages are zstd frames in v14, LZ4 blocks in v13.

```sh
cargo bench --locked --features simulation --bench log_shipping -- 2 > benches/results/log-shipping.csv
python3 benches/scripts/analyze_log.py
POLICIES=32:65536:1024,32:65536:4096 cargo bench --locked --features simulation --bench log_shipping > sweep.csv
python3 benches/scripts/analyze_log.py --sweep sweep.csv   # after:log_bytes:inline_bytes
```

A _read session_ is open plus query; a _write session_ is open, query and save.

32 transactions or 64 KiB, sealed past 4 KiB, is the default. On the large
database it writes 5.1 KB per session (16 tx or 16 KiB, all inline: 13.0 KB;
v13 at its bindings' cadence: 3.1 KB) at 4.72 round trips (5.24; v13 5.62).
Sealing past 1 KiB writes 3.2 KB, but a small commit then costs 1.3 round
trips more often (a seal without its cached owner's next commit); 8 KiB saves
0.03 round trips for 40% more bytes. Never sealing at 64 KiB writes 33 KB.

## Findings

- **Opens are one round trip, or two cold.** Open reads the commit record, and
  the stored values it names, if any; a cold owner also reads the hint with it
  and prefetches pages in a second. Without a cache, v13 at the bindings'
  cadence took 4.9 RT to open (probing up to 60 log segments); v14 takes 2.0.
- **Reads cost a few gets.** With a cache an open is one get of the record
  (v13: 27 gets per read session at the bindings' cadence, replaying the log's
  segments), and a session reads 4.1 KB on the large database instead of
  54.5 KB.
- **Commits write a few KB.** A write session writes 6.8 KB on the large
  database with a cache (v13: 3.1 KB, the previous v14 default: 17.3 KB):
  the record, bounded by the seal, plus the checkpoint's pages. Read and
  written together, v14 moves 80% fewer bytes than v13 there.
- **Saves.** A small save is one put of the record, one round trip, with the
  seal (cached) and the previous record's garbage deletes in it. A
  checkpointing save adds two (the pages, then the record), plus one per 64
  pages past the first 64; the commit before it keeps its transaction inline,
  as the checkpoint drops the log. Saves average 1.19 RT with a cached owner
  on the large database (v13 1.07, worst 8; v14 worst 5).
- **Storage.** 24% fewer stored bytes than v13 at the bindings' cadence.

## Possible improvements, not implemented

- **Checkpoint with the commit.** A checkpointing save could write the
  previous record's log pages in the commit's round trip, then a record with
  only the new transaction: one round trip off checkpointing saves.

Remaining limits: simulated latency only, a uniform RTT for every request, no
bandwidth model, a single owner and no real backend. The end-to-end benchmark
against a Restate server is in
[the SQL benchmark](../../../typescript/tests/sql/bench.ts).
